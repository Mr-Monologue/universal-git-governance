# 通用嵌入式 C 编程规范（Embedded C Coding Standard）

> **Draft 适用边界**：Doxygen 强制要求保持不变；11 项默认风格已由所有者批准，见第 16 节。
> 既有项目正式规则优先；批准不构成稳定版发布。历史见 [OPEN_DECISIONS.md](OPEN_DECISIONS.md)，
> 审查入口见 [REVIEW_CHECKLIST.md](REVIEW_CHECKLIST.md)。

> **定位**：面向个人、团队及 AI Agent 的通用嵌入式 C 开发基线，供 Engineering System 的 `standards/embedded-c/` 使用。本文件不绑定具体 MCU、IDE、RTOS 或商业/开源许可证。

>

## 1. 规则语言和适用范围

- **必须（MUST）**：默认强制；存在实际冲突时须按项目既有正式要求处理并记录偏离。
- **应该（SHOULD）**：强烈推荐；在技术、性能、兼容性有合理理由时可调整。
- **可选（MAY）**：取决于项目类型和成本收益。
- 不得为了满足形式规则而引入未定义行为、降低实时性或改变现有 ABI。
- 继承旧工程时，先识别已批准的编码规范、编译器版本与兼容性边界；**不得擅自全量格式化或重命名现有接口**。
- MISRA C 需指定适用版本、规则范围、偏离流程和相应工具；仅执行本规范**不代表**通过 MISRA 合规审查。

### 1.1 预置项目 Profile（建议）

| Profile | 适用场景 | 额外要求 |
| --- | --- | --- |
| `general-embedded` | 常规裸机/BSP/驱动/业务固件 | 基线全部 MUST；动态内存是否允许由项目决定 |
| `hard-realtime` | 电流环、ISR、固定周期控制 | 热路径无不可控阻塞/分配；测量 WCET 或时间预算 |
| `safety-critical` | 具有明确功能安全要求的系统 | 在基线外引入正式标准、工具链证据、审查与偏离台账 |
| `legacy-compatible` | 厂商 SDK/旧工程维护 | 兼容原 ABI/规则；仅对新写代码渐进引入 |

Profile 是待项目批准的建议，不因本文件存在而自动在其他项目启用。

## 2. 文件组织与模块边界

### 2.1 一组 `.h / .c` 文件的责任

- **必须**：对外函数声明、公开类型及常量放在 `.h`；函数实现、内部状态和私有辅助函数放在 `.c`。
- **必须**：非公开全局对象和内部函数使用 `static` 限制链接可见性；不在头文件定义普通非 `static` 变量。
- **必须**：头文件可独立编译/解析，包含其公开声明真正需要的类型依赖；使用唯一的宏式 include guard。
- **应该**：每个 `.c` 首先包含自己的对应 `.h`，以尽早暴露头文件缺失依赖问题。
- **应该**：用 `#include <...>` 表示标准/工具链头文件，用 `#include "..."` 表示工程头文件；具体排序由项目格式配置统一。
- **必须**：不得循环包含造成不透明的依赖耦合；若存在跨模块关系，优先使用接口/前向声明降低依赖。
- **必须**：对新增公众 API 统一使用模块前缀，如 `adc_scale_convert_mv()`，防止 C 的全局符号空间冲突。
- **可选**：如头文件同时供 C++ 调用，可提供 `extern "C"` 包装；C-only 项目无须强制。

### 2.2 头文件防护

```c
#ifndef ADC_SCALE_H_
#define ADC_SCALE_H_

#include <stdint.h>

/* Public declarations */

#endif /* ADC_SCALE_H_ */
```

Guard 名应与项目约定一致，避免与第三方库同名；`#pragma once` 可由项目启用，但不能在未批准的跨工具链项目中强制替代宏式 guard。

## 3. 格式和命名（可由工具强制）

| 项目 | v0.1 已批准默认值 | 说明 |
| --- | --- | --- |
| 缩进 | 4 个**空格**，不使用 Tab 字符缩进 | 修正原文“4 空格同时使用 Tab”矛盾 |
| 大括号 | Attach / K&R，`{` 与条件/函数签名同行 | 可由项目覆盖；不擅自重排历史代码 |
| 行宽 | 100 列软限制 | 比原 80 列更适合现代代码；项目可选 80/120；字符串、宏、文档链接可按需例外 |
| 函数/变量 | `snake_case` | 命名表达业务/物理意义，不使用字母堆叠 |
| 公开函数 | `module_action()` | 统一模块前缀，避免同名冲突 |
| 宏/枚举值 | `MODULE_UPPER_SNAKE_CASE` | 避免无意义的通用宏名 |
| 私有静态对象 | 模块内自洽命名即可 | 不强制 `g_`/`p_`/`pf_` |
| 类型 | 语义化 `module_type`；不普遍使用 `_t` 后缀 | `_t` 在部分 POSIX 环境存在名称保留风险，跨平台时需谨慎 |

**必须**：格式一致性通过仓库批准的 `.clang-format` 执行；不得在 PR 中混入与任务无关的大范围格式化。

**必须**：标识符不使用实现保留前缀（例如前导双下划线，或下划线后紧跟大写字母）；公开标识符不得使用含混的单字母名（局部常见循环变量可例外）。

**应该**：避免把数据类型写进无意义的匈牙利命名，例如 `p_data`、`pf_handler`；指针所有权、长度和只读属性应当由类型与 API 契约表达。

## 4. 数据类型、转换与数值安全

- **必须**：协议字段、硬件寄存器宽度、二进制格式使用合适的 `uint8_t`、`uint16_t`、`uint32_t` 等（仅在工具链提供相应精确宽度类型时）；大小和容器容量优先用 `size_t`。
- **必须**：明确区分 *位宽*、*数值范围*、*计量单位*，不能把 `uint16_t` 当成自动保证物理量合法的手段。
- **必须**：对可能丢失范围或符号信息的转换，在转换**之前**验证范围；强制类型转换本身并不会让转换安全。
- **必须**：检查除数为零、加乘溢出、数组边界、移位位数和位操作类型；避免有符号溢出等未定义行为。
- **必须**：位掩码优先使用无符号操作数；当移位数由输入提供时验证其是否小于被移位类型的位宽。
- **应该**：使用 `UINT32_C(...)` 等标准宏表达特定宽度整数常量；根据目标编译器和场景使用恰当后缀。
- **不强制**：“所有浮点运算都应避免”。需要时分析 FPU、精度、实时执行时间和 NaN/Inf 风险；定点运算亦必须分析量化误差和溢出。
- **应该**：涉及单位换算时在名称/API 文档中显式给出单位，如 `speed_rad_s`、`timeout_ms`、`current_ma`。

### 4.1 缩窄转换示例

```c
#include <stdint.h>
#include <stdbool.h>
#include <limits.h>
#include <stddef.h>

static bool to_u16(uint32_t value, uint16_t *out) {
    if ((out == NULL) || (value > UINT16_MAX)) {
        return false;
    }
    *out = (uint16_t)value;
    return true;
}
```

## 5. 指针、数组与内存生命周期

- **必须**：任何解引用都必须具有有效性依据；对**允许空值或接收外部输入**的指针做检查，对由调用约束保证非空的内部路径不要求无意义地重复判空。
- **必须**：接口说明数据的读写方向、缓冲区长度、所有权、有效期以及是否允许别名或重叠。
- **必须**：缓冲区 API 使用显式容量参数；所有索引和长度计算保证不越界。
- **必须**：不返回局部自动对象地址；异步/DMA 操作不得使用已失效的栈地址或提前释放的缓冲区。
- **必须**：字符串操作确保输出以 `\0` 结尾并处理截断；`strncpy` **不保证**对过长字符串自动加 `\0`，不能作为普遍意义的“安全函数”。
- **必须**：`memcpy` 仅在源/目标缓冲区长度正确且不重叠时使用；允许重叠时改用 `memmove`。
- **应该**：优先静态或由调用方提供的缓冲区；是否允许动态分配由项目或执行域决定，而不是对所有嵌入式项目一刀切禁用。
- **必须**：禁止在对时间确定性有硬要求的 ISR/实时热路径中做无法证明上界的内存分配和阻塞操作。
- **建议**：允许将栈上数组和大对象的使用限额配置为静态分析规则或链接/编译预算。

## 6. 函数与公开 API 契约

- **必须**：函数职责聚焦，参数含义明确；返回类型、错误状态和副作用不得隐含。
- **应该**：当参数显著过多（例如超过 5 个）时审查是否适合用参数结构体；不是机械拒绝。
- **必须**：关键错误不能被忽略；对于可安全忽略的结果，明确依据，不强制把所有 `void` 或无错误语义的结果包装成检查。
- **必须**：接口设计区分调用成功、参数错误、状态错误、硬件错误；返回错误码还是通过输出参数返回应保持模块内一致。
- **应该**：公开 API 避免对外暴露非必要可变全局状态；需要全局资源时通过模块实例/上下文或受控访问方法表达。
- **必须**：对外承诺线程安全、ISR 可调用或可重入时必须有证据，不能根据“函数短小”推断。
- **必须**：如果单位、范围、调用前置条件、是否阻塞、所有权或中断环境有约束，文档必须明确写出。

## 7. 流程控制与错误处理

- **必须**：流程尽可能明确；复杂嵌套优先拆函数或使用 guard clause（提前返回），但不得改变短路求值所依赖的副作用。
- **应该**：`switch` 枚举分支覆盖所有业务状态；`default` 的存在与否依据编译器枚举覆盖告警与项目策略决定，**不能以空 `default` 掩盖遗漏**。
- **允许（有条件）**：`goto cleanup` 用于一个函数内多资源释放/集中清理，但不得形成复杂跨层跳转；原文“全面禁止 goto”调整为推荐结构化控制流。
- **必须**：错误处理不得静默丢失重要原因，也不得在 ISR 内强制同步写日志；可返回错误、递增计数或将事件推入无阻塞队列。
- **应该**：限定重试次数、超时时间及失败回退状态；通信和硬件操作不得永久阻塞无退出策略。
- **必须**：初始化和反初始化流程状态明确，失败路径释放已获取的资源。

## 8. 宏、预处理器与编译器扩展

- **必须**：复杂多次求值宏慎用；对可能产生副作用的表达式优先改用带类型的函数或 `static inline`。
- **必须**：宏形参和整体表达式妥善加括号；宏命名体现模块归属。
- **应该**：配置开关通过统一配置头文件或构建系统注入，不在多个源文件中分散定义相冲突的开关。
- **必须**：硬件寄存器、链接段、packed、interrupt 等编译器扩展集中在平台适配层并说明适用工具链；不得谎称这些扩展属于 ISO C。
- **可选**：C11 `_Static_assert` 用于验证结构体布局、类型宽度和编译期约束；C99 项目采用工具链允许的兼容方式。

## 9. 并发、ISR、RTOS、DMA 与硬件接口

- **必须**：共享状态明确生产者/消费者及上下文（ISR、任务、主循环、DMA、第二核心）。
- **必须**：`volatile` 只表达某些访问的可观察性要求，**不提供原子性、锁、跨核内存顺序或 cache coherency**。
- **必须**：根据平台使用临界区、原子操作、内存屏障、RTOS 同步原语或无锁数据结构；设计前确认编译器、目标核及平台支持。
- **必须**：ISR 中不做不受控阻塞、等待互斥锁、堆分配或高延迟日志；中断中调用 RTOS API 必须使用对应 ISR 安全版本。
- **必须**：DMA 缓冲区地址/对齐/缓存维护/有效期的要求用 API 契约或平台文档表达。内存屏障和 cache clean/invalidate 的时机不能靠 `volatile` 替代。
- **应该**：周期性算法标注调用频率、时间预算和状态更新时序；高优先级 ISR 和控制环通过测量验证执行时间上限。
- **必须**：MMIO 寄存器访问使用正确的硬件定义、读改写语义与屏障要求；不得直接通过普通指针“猜测”寄存器访问合法性。
- **必须**：确认 RTOS 调度、任务栈和优先级不会引入数据竞争或优先级反转。

## 10. Doxygen 文档规范（强制）

> **本章为强制基线**。新建和修改的用户维护 `.h/.c` 文件使用 Doxygen 注释记录文件职责与 API 契约。普通 `//`、`/*...*/` 可用于实现说明，但不能代替公开接口的 Doxygen 文档。

### 10.1 必须文档化的对象

| 对象 | 要求 | 位置 |
| --- | --- | --- |
| 每个新建 `.h` / `.c` | `@file`、`@brief`，必要时用途/依赖、版权声明 | 文件顶部 |
| 对外公开函数 | `@brief`，每个形参的 `@param`，非 `void` 的 `@return` 或 `@retval`；必要时 `@pre`/`@post`、`@warning`、`@note` | **优先在头文件声明处** |
| 公开 `struct/enum/typedef` | `@brief`，对含义不明显的成员/枚举值逐项说明 | 头文件 |
| 对外宏与常量 | `@brief` 或 `/**< ... */` 描述用途/单位 | 头文件 |
| 内部复杂函数 | `@brief` 或有意义的实现说明，视复杂度决定细节 | `.c` |
| ISR/RTOS/DMA API | 说明允许的调用上下文、阻塞/重入、资源所有权、同步前置条件 | 对外声明或模块文档 |
| 控制/算法公式 | **先列符号及单位/物理意义**，再给计算关系；代码注释重点说明数值约定 | 适用函数/算法文档 |

Doxygen 统一使用 `/** ... */` 作为多行注释形式、`@command` 作为命令风格；允许 `/**< ... */` 描述枚举值/成员。不混用普通巨型横幅注释与非 Doxygen 块作为 API 文档。

### 10.2 文件头模板

```c
/**
 * @file adc_scale.h
 * @brief ADC 原始计数到毫伏的换算接口。
 *
 * 模块不依赖硬件寄存器；调用方负责提供参考电压及满量程码值。
 *
 * @note 本模块不执行采样和滤波。
 */
```

许可证声明**根据仓库实际许可证**添加，例如 MIT 项目可使用 `// SPDX-License-Identifier: MIT`；闭源项目按照企业要求添加版权与保密声明。不要让 Agent 擅自生成虚构作者、组织、创建时间或许可证。文件的历史版本与修改记录**由 Git 负责**，一般不在每个文件头重复 `@version/@date/@revision_history`，除非项目有法规或外部交付要求。

### 10.3 公开函数模板

```c
/**
 * @brief 将 ADC 原始码值换算为毫伏。
 *
 * @param[in] raw_code 原始 ADC 码值，范围 [0, full_scale_code]。
 * @param[in] full_scale_code 满量程 ADC 码值（不是码值总数），必须大于 0。
 * @param[in] reference_mv 参考电压，单位 mV，必须大于 0。
 * @param[out] result_mv 换算电压，单位 mV；成功后写入；不允许为 NULL。
 * @retval ADC_SCALE_OK 转换成功。
 * @retval ADC_SCALE_INVALID_ARG 参数不合法，输出不修改。
 * @note 无动态内存分配；可重入（不同调用不得同时写同一输出位置）。
 */
adc_scale_status adc_scale_convert_mv(uint16_t raw_code,
                                      uint16_t full_scale_code,
                                      uint32_t reference_mv,
                                      uint32_t *result_mv);
```

只写 `@param data 输入数据`、`@return 返回结果` **不合格**：必须说明数据的意义、单位、范围、错误条件或输出约束（只填写有实际意义的项目）。如不适用，无须每个函数机械添加所有标签。

### 10.4 算法与公式的注释要求

- **先定义变量**：英文标识符、数学符号、单位、物理意义、取值约定。
- **再解释公式及近似条件**：如 `iq_ref_a` 与 `iq_measured_a` 是否为峰值还是 RMS、角速度是 `rad/s` 还是 `rpm`。
- **实现中标注**：量化/Q 格式、采样周期、饱和限幅、积分状态、单位转换和异常行为。
- **禁止**：没有定义变量的孤立公式；仅复述代码动作的注释；与实现不一致的“复制型文档”。

### 10.5 文档检查与 Doxygen 配置

推荐给实际项目的 `Doxyfile` 配置项：

```ini
EXTRACT_ALL           = NO
WARNINGS              = YES
WARN_IF_UNDOCUMENTED  = YES
WARN_IF_DOC_ERROR     = YES
WARN_NO_PARAMDOC      = YES
WARN_AS_ERROR         = FAIL_ON_WARNINGS
```

执行时需对照已安装 Doxygen 版本确认配置项支持情况。**严格文档告警门禁仅对纳入本项目文档范围的用户维护代码强制执行**；第三方 HAL/SDK、代码生成文件可用 `EXCLUDE` 或独立配置，避免不必要的海量告警。

对于 Doxygen 无法表达的性能上界、具体安全证明、单元测试结果，要用测试/分析文档补充，而不是把 `@warning` 当成认证证据。

## 11. 日志与可观测性

- **必须**：错误有明确的可观察出口，例如错误码、状态字段、计数器、异步事件、日志之一。
- **不能强制**“每次调用失败必须写日志”，尤其不适用于控制中断和低功耗路径。
- **应该**：日志记录事件类别、模块、必要参数和上下文；避免泄漏密钥、私密信息或在频繁路径大量输出。
- **建议**：将诊断级别编译期裁剪、运行期过滤，并明确内存/带宽上界。

## 12. 安全、鲁棒性与可测试性

- **必须**：针对边界值、空值、异常状态和资源不足路径做可观察的处理；不以“理论上不会发生”作为免验证依据。
- **必须**：输入源不可信（通信帧、文件、外部设备数据）时验证长度、标识、范围、CRC/认证（如果协议定义）及解析状态。
- **必须**：库接口不隐含无限阻塞、强行断言或自行复位；系统级故障策略由上层配置和调用约束决定。
- **应该**：模块依赖可注入或可替换，以便在 PC 做单元测试/SIL；硬件访问与纯算法适当分离。
- **建议**：关键计算具备明确的极值、误差和有效输入测试；对指针和数组使用静态分析、编译器告警辅助审查。

## 13. 工具链与最小验证

| 工具 | 职责 | 强制程度 |
| --- | --- | --- |
| `clang-format` | 代码排版一致性 | 对使用此标准的新代码必须；版本由项目冻结 |
| C 编译器警告（GCC/Clang/ARM/IAR 等） | 诊断类型、声明、隐式转换等问题 | 必须；告警清单与例外由项目配置 |
| 单元测试/目标测试 | 验证正常、边界和故障路径 | 对有行为改动的模块必须提供适当证据 |
| `clang-tidy` / `cppcheck` / 商用分析工具 | 风险与可移植性审查 | 应该启用至少一种适用方案 |
| `doxygen` | 解析 API 文档与检查注释质量 | 对新建/修改的公开 API 必须验证，项目逐步建立自动检查 |
| MISRA 规则检查器 | 形式化地审查选定 MISRA 规则 | `safety-critical` 或项目要求时启用 |

示例命令（实际编译配置以项目工具链为准）：

```bash
clang-format --dry-run --Werror path/to/module.c path/to/module.h
# 例：宿主机纯算法模块，非面向所有 MCU 的通用参数
cc -std=c11 -Wall -Wextra -Wpedantic -Wconversion -Wsign-conversion -c module.c
# 生成 Doxygen 文档并根据项目 Doxyfile 检查 warning
# doxygen Doxyfile
```

不得声称“clang-format 通过就等于符合本规范”，因为格式化无法证明 API 契约、并发安全或 MISRA 合规。

## 14. Agent 读写代码的操作要求

1. **开始前**：识别项目 C 标准、芯片平台、编译器、RTOS、原有编码规范和已有文件风格。
2. **若有新建模块**：定义职责、公开 API、错误码、状态与资源所有权；先起草 Doxygen 契约，再实现代码。
3. **编写时**：遵守当前任务范围，不修改无关文件；厂商生成代码不要直接覆写，除非项目要求。
4. **修改现有函数**：同步更新其 Doxygen（参数、返回值、单位、时序、上下文），不得留下过期注释。
5. **验收时**：运行可用的编译、格式、测试、文档检查，记录具体命令和真实结果。无法运行需明确说明原因。
6. **禁止**：捏造测试通过、生成虚构版权信息、在未授权情况下全面格式化遗留工程、把建议 Profile 自动升级为强制安全认证。
7. **与 Git 的关系**：仅按独立 Git Governance Skill 及任务授权执行分支、提交、发布；本标准不赋予任何 Git 操作权限。

## 15. 与原始 Checklist 的对应和修订摘要

| 原始主题 | 本版处理 | 主要理由 |
| --- | --- | --- |
| 标准 C、定长类型、初始化、边界检查 | 保留并精细化 | 区分平台扩展、数值范围与行为约束 |
| “避免所有隐式转换” | 改为关注有损/危险转换 | 强制类型转换本身不保证安全 |
| “避免浮点，尽量整数” | 改为按硬件和实时场景判断 | FPU、精度、误差和性能权衡 |
| “4 空格，使用 Tab” | 明确 4 个空格，不使用 Tab | 原文自相矛盾 |
| 80 字符行宽 | 建议 100，项目可覆盖 | 改进可读性，不视为安全规则 |
| 匈牙利命名、`p_`/`pf_`、`_T`/`_t` | 不再通用强制 | 更鼓励清楚语义与模块命名；兼容已存在项目 |
| 头文件保护、宏大写 | 保留 | 避免重定义与命名冲突 |
| `switch` 必须有 `default` | 改为按枚举覆盖/编译器策略 | 避免空 default 反而隐藏遗漏 |
| 绝对禁止 `goto` | 允许局部集中清理 | 多资源失败路径更易审查 |
| 任何指针都要检查空 | 按契约和可信边界检查 | 兼顾安全、性能与代码冗余 |
| 任何函数返回值都要检查 | 聚焦可失败且有必要处理的状态 | 返回值语义决定检查方法 |
| 函数失败必须记日志 | 要求可观测，不强制同步日志 | 兼顾 ISR 和实时性 |
| `strncpy` 被列为安全拷贝 | 修正为必须检查终止符与截断 | 防止未终止字符串被误用 |
| 大段版权头、手工版本履历 | 建议 SPDX + Git 历史 | 降低过期信息；企业要求优先 |
| 注释格式 | **Doxygen 强制** | 便于 API 契约、提取与自动化检查 |
| MISRA C checklist | 保留原则，合规以选定标准/工具评估 | 防止误以为“通过自制 Checklist 就合规” |

批准日期：2026-10-20（Asia/Hong_Kong）。批准来源：当前 Task 010 对话中所有者明确回复“批准全部 11 项”，并再次确认。

本节是默认值的唯一规范性维护源；已有项目正式规则、组织合规及目标工程限制优先。
下表未标“建议”的值为采用本规范且无项目覆盖时的默认要求；C11 与标识符语言为建议。
批准风格不等于发布稳定版：规范包仍为 Draft 0.1.0，Skill 仍为 Draft / Preview 0.1.0。

| ID | 已批准默认值 | 项目覆盖与例外 |
| --- | --- | --- |
| C-STYLE-01 | Attach / K&R：函数和控制结构左括号同行 | 已有项目风格优先；不做无关重排 |
| C-STYLE-02 | 4 个空格；不使用制表符缩进 | 项目批准的 .clang-format 执行 |
| C-STYLE-03 | 100 列软限制 | 项目可选 80/120；不机械拆分字符串、宏和链接 |
| C-STYLE-04 | snake_case；公开函数/符号使用模块前缀 | 不普遍强制 g_/p_/pf_；保留已有 ABI |
| C-STYLE-05 | 类型用语义化名称，不普遍使用 _t；宏及枚举常量 UPPER_SNAKE_CASE | 第三方 API、RTOS 和已有类型约定优先；避免保留命名空间 |
| C-STYLE-06 | 新项目建议 C11；兼容已有 C99；C23 单独验证 | 目标工具链和项目安全认证要求优先 |
| C-STYLE-07 | 文件/API 必须 Doxygen；个人中文项目默认中文 | 团队/国际项目可用英文；标识符建议英文，参数名与代码一致 |
| C-STYLE-08 | 变更范围内执行可用格式检查、编译告警、公开 API Doxygen 校验和相关测试 | 缺工具报告 NOT RUN；项目可提高门禁 |
| C-STYLE-09 | 不默认宣称 MISRA 合规 | 项目选定标准版本、风险等级和偏离流程 |
| C-STYLE-10 | 默认 variable == constant；不强制 Yoda 条件 | 静态检查、团队约定和可读性优先 |
| C-STYLE-11 | @file、@brief 和真实版权/许可证；历史使用 Git/Changelog | 不伪造作者、日期；不强制冗长文件历史表；许可证须有实际依据 |
