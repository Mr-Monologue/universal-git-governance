# Universal Git Governance — v3.0

> **适用范围**：个人、开源、团队和企业软件项目；适用于人工开发者及 Codex、Cursor、Claude Code 等不同 Agent。
>
> **设计目标**：少量稳定规则、可审阅的提交、清晰的候选验证与对外发布边界、真实贡献归属和可追溯操作。
>
> **边界**：专注 Git 代码协作、分支与发布治理，不替代具体项目的技术规范和测试策略。

## 1. 适用优先级与执行原则

1. **法律、安全与组织强制政策**优先于本规范；仓库现有、已明确批准的贡献和发布规则优先于本规范的默认分支模型。
2. 本文中的三长期分支方案是**推荐的默认模型**，**不是自动修改现有仓库结构的授权**。发现已有主分支名称或其他工作流时，先检查并遵循已有规则；调整须经项目负责人明确批准。
3. 没有授权不执行影响 Git 历史或远端的操作。读取状态、说明方案与给出命令，不等于获得执行许可。
4. 不能把某一步的授权推导成后一阶段的授权。开发完成、测试通过、提交成功、推送成功、PR 建立、合并完成、创建 Tag、公开 Release 和部署是不同状态。
5. 保留真实的 Author、Committer、共同作者和审核信息；不将仅仅使用某种 AI 工具自动解释为该工具是代码共同作者。
6. 出现未知修改、冲突或无法证明的验证结果，先保留已有成果，再停止有风险的下一步，不擅自清理或回退。

## 2. 默认分支结构

### 2.1 分支职责

| 分支 | 生命周期 | 定位 | 常规来源 | 对外发布语义 |
| --- | --- | --- | --- | --- |
| `main` | 长期，默认分支 | **经批准的正式稳定基线**，外部阅读的默认入口 | `release` 经批准晋升 | 正式版本 |
| `develop` | 长期 | 日常集成、基础构建与持续验证 | 已验收的 `feature/*`，必要的发布修复回同步 | 非正式版本 |
| `release` | 长期，固定唯一名称 | **内部测试、RC、有限范围预览、回归和发布稳定化** | 由 `develop` 晋升的某一次候选 | 非正式版本 |
| `feature/*` | 短期 | 独立开发、缺陷修复、重构、试验、文档与治理变更 | 默认从 `develop` 派生 | 不直接发布 |
| `hotfix/*` | 短期、例外 | 已对外版本的紧急修复 | 仅逐次批准后，从对应正式基线派生 | 需单独验证与发布 |

标准代码流：

```text
                ┌────────── feature/任务A ─────────┐
                │                                  │
main ───────> develop <──────────────────────────────┘
  │               │
  │               └────候选集成───> release
  │                                  │
  └────<────正式验收 + 当次授权───────┘
            release → main
```

- `main` 是**发布结果**，不是用来验证尚未正式接受功能的分支。
- `develop` 是**持续集成的落点**，不是所有人直接改代码的日常开发分支。
- `release` 是**进入 `main` 之前**的候选验证点，**不是**从已公开的 `main` 向后同步的发布备份分支。
- `feature/*` 负责执行具体任务，允许尚未完成的本地迭代；未满足验收不得合入 `develop`。
- 若仓库公开，`release` 仍可能对外可见。“内部候选”是发布语义，**不是访问控制**。

### 2.2 新仓库初始化

**只有在明确要求初始化这套分支结构时**，才从同一初始化提交创建 `main`、`develop`、`release`：

```text
main     A   # 初始化提交
├─ develop A
└─ release A
```

- 三个分支最初指向**同一个 SHA** 是正常的；不必为了创建分支而制造额外 Commit。
- `main` 设为仓库默认分支；初始化提交可以只是目录或 README，**不意味着产品已正式发布**。
- 如果分支已存在，不能重建、重置或强制覆盖。若当前仓库使用 `master`、`trunk` 或其他既有制度，不自动改名或改流程。
- 初始化本地分支、远端创建、设置默认分支和启用保护是**不同动作**，分别以实际授权和平台权限为准。

### 2.3 固定分支与短期命名

- 长期分支仅为默认的 `main` / `develop` / `release`。
- **不创建** `release/v1.0.0`、`release/phase-2` 或其他版本化 `release/*`；固定的 `release` 一次承载一个受控候选周期。
- 短期分支命名为 `feature/<scope>`，推荐 `feature/<module>-<task>`，小写 ASCII 和连字符，例如 `feature/auth-timeout-fix`、`feature/docs-git-policy`。
- `hotfix/*` 是严格受控的紧急例外，不成为常规开发捷径。

## 3. 何时进入 `feature/*`

**判断依据是“是否构成独立可验收的变更任务”，而非修改行数。**

| 场景 | 默认处理 |
| --- | --- |
| 新增功能或接口 | 从 `develop` 创建独立 `feature/*` |
| 修复 `develop` 中发现的普通缺陷 | 从 `develop` 创建 `feature/*`，完成后回合并 |
| 独立重构、实验或需要可单独回退的变更 | 创建独立 `feature/*` |
| 文档、CI、配置或依赖更新 | 默认在对应 `feature/*` 中完成；不因为改动小就绕开审核 |
| 同一功能开发中连续修正多个相关文件 | 保留同一个 `feature/*`，直到整体验收；不必每次改动另建分支 |
| 在 `release` 发现发布阻断缺陷 | 基于当前候选创建短期修复分支，严格只修候选问题，修复同步 `develop` |
| 已发布版本的紧急事故 | 申请单次 `hotfix/*` 例外，按专门批准的修复链操作 |

- `feature/*` 应有明确目标、边界和验收条件；不让一个长期 feature 无限制收纳不相关工作。
- 试验失败可以停止，不合并到 `develop`；不用为未完成试验制造“通过”的结论。
- **不要求等所有计划功能完成才发布。** 发布范围由某一次明确选定的候选功能集合决定。

## 4. 合并与发布流程

### 4.1 常规开发：`feature/* → develop`

1. 检查当前分支、已有更改、目标分支与可用远端；不得覆盖用户未提交的修改。
2. 基于 `develop` 创建 `feature/*`，按任务范围开发。
3. 执行与变更影响相匹配的构建、静态检查、单元测试与其他必要验证；`NOT RUN` 不得写成 `PASS`。
4. 完成审核与授权后，合入 `develop`；有远端时优先 PR/MR。默认可用 **Squash Merge** 让集成历史简洁，必要时可用 Merge Commit 保留多个有价值的提交。
5. 删除短期分支或清理提交仅在确认已合并、无保留需求且得到相应授权后进行。

### 4.2 内部候选：`develop → release`

- 由负责人明确选择**本次候选范围**，而不是不加选择地把开发中未完成的功能推向 `main`。
- 在集成构建通过、重大已知风险说明清楚后，按授权将候选并入固定 `release`；推荐 Merge Commit 记录候选边界。
- `release` 只做 RC 测试、回归、缺陷修复、必要配置与发布文档修订；**禁止顺带开发新功能**。
- 每次候选有唯一、不可变的候选提交定位；如需标识，使用 `vX.Y.Z-rc.N` Annotated Tag。修复后产生**新的** RC Tag，不挪动旧 Tag。
- 发布阻断修复应从**当前 `release`** 派生短期修复分支，按批准路径合回 `release`；将真正的修复变更准确同步至 `develop`，避免重复提交或覆盖尚未发布的新工作。
- 候选通过之前**不允许**把候选合入 `main`。一个固定 `release` 分支原则上只承载一个验证中的候选周期；并行多版本维护需另行审议工作流。

### 4.3 正式发布：`release → main`

必须同时满足：

1. 当前候选的发布内容已明确，并有实际可核实的测试、审查与验收结果。
2. **本次 `release → main` 具有单独、明确的晋升授权**；上一次发布授权不适用于下一次。
3. 按仓库机制通过 PR/MR 或经批准的本地受控合并，禁止跳过 `release` 直接让常规 `feature/*` / `develop` 晋升 `main`。
4. 发生合并冲突、发布内容漂移、新引入未经批准的修改，必须暂停，重新核对发布差异和验证结果。
5. 推荐使用 **Merge Commit**，确保正式发布边界清晰；核对 `main` 最终内容并完成适用的最终构建/验证。
6. 正式 Annotated Tag `vX.Y.Z` **创建在实际发布的 `main` Commit**，不要提前在 `release` 上创建正式 Tag；创建、推送 Tag 和公开 Release 均单独确认权限。
7. 将候选期修复回同步 `develop`；若已有相同改动，必须核对后避免重复，不盲目合并或 cherry-pick。

> 为什么不是 `develop → main → release`？因为这样会先把未经候选回归的功能放进对外默认分支，违反 `main` 的稳定发布语义。

### 4.4 发布后与异常分支

- 下一候选从**新的 `develop`** 进入长期 `release`；不强推、不重设旧 Tag、不开新 `release/v*`。
- 如果紧急修复已发布的 `main`，应首先识别 `release` 是否包含其他未发布改动。**不得为了坚持常规链路而把无关候选内容带入紧急正式版本。** 必要时申请并记录直接修复正式基线的单次紧急例外，并把结果同步到其他长期分支。
- 已发布内容的问题通过新的修复提交/新版本处理；不擅自重写公共历史、强制推送或移动既有 Tag。
- 远端长期分支默认通过 PR/MR 合并；`main`、`release` 禁止常规直接推送，`develop` 也应避免直接推送。若平台不支持 PR/保护规则，仅执行经过明确批准的受控本地合并与同步；不得宣称远端已有门禁。

## 5. Tag 与 Release

> **Git Tag 是仓库范围的固定引用，不隶属于某个分支。** 所谓“RC Tag 在 release、正式 Tag 在 main”指的是**创建时所指向的提交与发布语义**，不是 Tag 随分支移动。

| 标识 | 例子 | 对应提交 | 用途 |
| --- | --- | --- | --- |
| 候选 Tag | `v1.2.0-rc.1` | 当次 `release` 候选提交 | 内测/回归定位 |
| 正式 Tag | `v1.2.0` | 已批准 `main` 发布提交 | 正式版可复现定位 |
| 后续修复 | `v1.2.1` | 新的正式发布提交 | 不覆盖原 Tag |

- 推荐遵循 SemVer `MAJOR.MINOR.PATCH`，具体版本号按项目成熟度确定。
- 正式 Tag 必须为 Annotated Tag，正文用中文记录**发布原因、主要功能、修复改进、已验证内容及已知限制**；RC Tag 也建议采用 Annotated Tag。
- Git Tag、托管平台上的 Release 页面、制品上传和生产部署彼此独立，不能互相冒充已完成。
- 发布候选应有明确的来源 SHA、发布记录与验证证据；不能因 `main` 生成了新的合并 SHA，就假定内容必然和已验收候选完全一致。

## 6. 中文 Commit 及审查记录

### 6.1 统一格式

默认使用 **Conventional Commits 的英文类型 + 可选 scope + 简体中文摘要**；公司或已有仓库对语言有明确政策时，以其规则为准。

```text
<type>(<scope>): <中文摘要>

变更原因：……
主要变更：……
影响范围：……
验证：通过/失败/未运行，并注明范围
```

- `type` 常用：`feat`、`fix`、`refactor`、`perf`、`test`、`docs`、`build`、`ci`、`chore`、`revert`。
- `scope` 优先使用仓库中真实存在的模块名称，不擅自发明难懂缩写；不需要 scope 时可写 `fix: ...`。
- 标题说明**产生了什么变化**，而不是“更新代码”“修复问题”“AI 优化”这种无法追溯的泛化描述。
- 影响行为的提交要记录改动理由与验证；不能编造测试数据、成功结果或不在 diff 中的改动。
- 破坏性变更使用 `feat(api)!:` 等标识并说明迁移和兼容影响。
- Commit/PR/发布说明中文优先；Git 分支、配置键、命令和代码标识可保持英文。
- **新规则不追溯重写历史提交**。

示例：

```text
feat(auth): 增加登录重试次数限制
fix(cache): 修复并发刷新导致缓存失效的问题
test(api): 增加鉴权失败路径的回归用例
docs(git): 完善正式版与候选版的分支边界
```

### 6.2 合并和晋升说明

- Feature PR 说明：任务目标、变更范围、风险、已运行的验证、尚未覆盖的验证。
- `develop → release` 说明：候选包含哪些功能、已知问题、回归计划及结果。
- `release → main` 的合并信息和正式 Tag 说明必须**面向用户描述这一版新增能力与修复**，不能只写“merge release”或“流程批准”。

### 6.3 作者、共同作者与工具署名

- Author / Committer 使用真实且经授权的身份；不能冒用他人身份，不能为了美化贡献者列表抹除真实作者。
- 不得将纯粹作为开发工具的 Cursor、Codex 或其他 Agent **凭默认模板自动添加为不准确的 `Co-authored-by`**；如果工具注入了错误署名，在提交前通过正常的消息模板、Git 配置或允许的流程移除。
- **不以规避共同作者展示为理由隐瞒实际第三方贡献、授权信息或组织强制审计要求。**
- `git commit-tree` 是低层 Git 原语，**可作为逐次授权的例外**，仅当正常提交路径无法避免错误工具署名且不会违反组织规则时使用；必须保留正确身份、父提交、暂存内容和适用签名要求，并先独立完成必要检查。它不会自动执行 `git commit` 钩子，**不得借此绕过安全、审查或质量门禁**。
- 完成提交后核查 `git log -1 --format=fuller` 和提交 Trailers，确认作者真实、内容准确且无误导性的工具共同作者信息。

## 7. Agent 操作边界

| 操作 | 默认规则 |
| --- | --- |
| 只读查看分支/日志/状态 | 可在当前任务相关范围内进行 |
| 修改源文件、执行测试 | 仅限本次任务授权的范围 |
| 初始化仓库、创建长期分支、改变默认分支/保护策略 | 单独授权 |
| 创建短期 `feature/*` | 仅在任务允许新建分支时执行；否则先报告方案 |
| `git add` / `commit` | 本次任务明确允许，且只暂存本次变更 |
| `push` | 指定远端/分支的单独授权 |
| 建立 PR/MR、合并到 `develop` 或 `release` | 对来源/目标与验证状态分别授权 |
| `release → main` | **硬门禁**：本次具体版本的明确晋升授权 |
| 创建/推送 Tag、公开 Release、部署 | 各自分别授权，不互相推导 |
| 修改既有 Git 历史、强推、删除分支/Tag | 默认禁止；须特殊明确授权且不违背强制安全规则 |

### 7.1 每次操作前

1. `git status --short --branch`、`git branch -vv`，必要时查看 `git remote -v` 与最近提交。
2. 识别用户已有修改、未知暂存与提交，不清理、不覆盖、不顺手带入任务。
3. 核对本次授权仅覆盖哪些文件、分支、远端和动作。
4. 若无远端，不能编造“已推送”“PR 已创建”“规则已受服务器保护”的状态。

### 7.2 暂存与提交

- Agent 默认**逐路径显式暂存**：`git add -- <path1> <path2>`；避免 `git add .`、`git add -A` 等不加区分的批量暂存。
- 提交前检查 `git diff --cached --name-status`、`git diff --cached --check`，必要时对主要差异逐文件核对。
- 发现暂存区包含非授权变更时停止提交，不擅自移除他人修改、覆盖或重置。
- 未授权不要执行 `git commit --amend`、`git rebase`、`git reset --hard`、`git clean -fd`、`git push --force` 等具有改写或清理效应的操作。

### 7.3 执行后报告

至少列出：

- 当前分支与实际提交 SHA（若有）；
- 修改范围、实际运行的测试及其 `PASS / FAIL / NOT RUN` 状态；
- 是否已经 Commit、Push、建立 PR、合并、打 Tag、公开 Release 或部署；
- 尚未完成的步骤、风险及下一项需要授权的操作。

**任务完成后停止；不得自动把“下一步推荐”当成新任务。**

## 8. 实施约定和典型流程

### 8.1 初次创建（仅作示意，不是自动授权）

```bash
git status --short --branch
git branch --list
# 确认 main 存在且已有初始提交，且 develop/release 不存在：
git branch develop main
git branch release main
# 如需要，单独授权后配置远端默认分支和保护策略
```

### 8.2 常规功能（命令示意）

```bash
git switch develop
# 仅在安全、已授权且有远端时更新本地 develop
git switch -c feature/login-rate-limit
# 实施更改并完成验证；只暂存授权的具体路径
git add -- path/to/changed-file
# 检查暂存清单与差异
git diff --cached --name-status
git diff --cached --check
# 已获本地提交授权才执行
git commit -m "feat(auth): 增加登录重试次数限制"
# PR/Push/Merge 均需要单独授权
```

### 8.3 默认合并矩阵

| 来源 | 目标 | 常规允许 | 条件 |
| --- | --- | --- | --- |
| `feature/*` | `develop` | 是 | 验收通过，合并获授权 |
| `develop` | `release` | 是 | 指定候选集成，测试计划明确 |
| `release` | `main` | 是，但严格受控 | 候选通过 + 当前版本的明确晋升批准 |
| 发布阻断修复分支 | `release` | 有条件 | 仅当前 RC 缺陷，受控修复 |
| 发布修复 | `develop` | 必须同步 | 确保不重复引入冲突 |
| `feature/*` | `main` | 否 | 常规开发禁止 |
| `develop` | `main` | 否 | 不跳过候选验证 |
| `main` | `release` | 否 | 不作为常规发布顺序 |

## 9. 规范演进

- 新仓库经批准可采用本规范；现有仓库应先做差异审查，**不能强制迁移既有流程**。
- 若业务要求高频持续部署、同时维护多个正式版本、或无法接受长期 `release` 的顺序候选模式，应通过明确的项目决策采用其他模型；不谎称本文是唯一的“Git 标准”。
- 本规范修订本身需记录版本与变更理由；Agent 不得擅自降低合并、发布或归属门禁。
